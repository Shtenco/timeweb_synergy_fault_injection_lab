# timeweb_synergy_fault_injection_lab

**SYNERGY / HIAI · Исследование №17 · Fault injection и переключение HTTP-реплик**

> **Статус доказательств:** Измерения на локальном стенде. Это рабочая исследовательская реализация, а не гарантированно готовая production-система.

## 1. Цель и постановка задачи

Исследовательская тема: **Fault injection и переключение HTTP-реплик**. Конкретная проверка в поставленном комплекте: Две локальные HTTP-реплики: отказ, retry, failover.

Проверяем воспроизводимость метода, корректность измерений и пределы интерпретации. Связанные рукописи и HTML доступны отдельно в закрытом авторском пакете; публичная публикация текстов до согласования с Timeweb Cloud исключена. Публикация в Timeweb Cloud возможна только после самостоятельной редакторской проверки и согласования.

## 2. Как устроен репозиторий

- `prototypes/` — исходный пакет сценариев, независимые функции и воспроизводимый CLI (для №01–15).
- `prototypes/real_experiments/` — измерительные сценарии там, где они действительно реализованы.
- `experiments/` — самостоятельный стенд №16–17.
- `results/` — исходные результаты JSON/CSV и/или графики, доступные в архиве; это архивные результаты, а не новые CI-прогоны.
- `article/` — редакционные материалы в отдельном офлайн-архиве; в GitHub по умолчанию не публикуются.
- `requirements.txt` — базовые Python-зависимости; для отдельных наборов данных возможны дополнительные шаги.

## 3. Быстрый старт

**Требования:** Python 3.10+ (желательно 3.11), Git, Linux/macOS/Windows. Для C++ бенчмарков нужен `g++` или `clang++`; для PyTorch обучения может потребоваться отдельная установка CPU-сборки PyTorch.

```bash
git clone https://github.com/Shtenco/timeweb_synergy_fault_injection_lab.git
cd timeweb_synergy_fault_injection_lab
python -m venv .venv
# Linux/macOS: source .venv/bin/activate
# Windows PowerShell: .venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

**Первый запуск:**

```bash
python experiments/fault_injection_lab.py --help
```

Рекомендуется сохранять временные и новые результаты в `results/local/`, не перезаписывая исходные измерения. Код из архивов был извлечен без изменения алгоритмов; выполнение полного набора в GitHub Actions на момент подготовки не подтверждено.

## 4. Экспериментальный протокол

1. Зафиксировать версии Python/библиотек, ОС, CPU и доступную память.
2. Использовать одинаковый объём вычислений для сравниваемых реализаций и сохранять seed, параметры, разбиение данных.
3. Собирать сырые измерения, включая отрицательные и неудачные прогоны. Не исключать результаты без указания причин.
4. Разделять correctness-check, тайминг, оценку потребления памяти и проверку статистической значимости.
5. Не переносить выводы локального эксперимента на другие среды без независимого повтора.

## 5. Что подтверждается и что не подтверждается

**Реальная область проверки:** Две локальные HTTP-реплики: отказ, retry, failover.

**Ключевое ограничение:** Нет production-кластера, сетевых разделений между датацентрами и высоких нагрузок.

Сохранённые JSON/CSV описывают прежние эксперименты; сами по себе они не являются независимой верификацией. В проектах с пометкой `simulation` или `synthetic` нельзя писать о реальных LLM, реальной облачной инфраструктуре или production-доказательствах.

## 6. Как проверить результаты

- Изучить `results/` и установить наличие JSON/CSV для конкретного исследуемого эффекта.
- Сопоставить `article/РУКОПИСЬ.md` с реально доступными файлами измерений.
- Перезапустить эксперимент с новыми seed и сохранить сведения о среде.
- Проверить контрольные суммы выходных данных и отсутствие утечек обучения в тестовые данные, где применимо.
- Публиковать и положительные, и отрицательные результаты.
